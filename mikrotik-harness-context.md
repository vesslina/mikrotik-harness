# MikroTik Harness — контекст проекта для Claude Code

## Раздел 1. Суть проекта

**Идея:** LLM-агент, который умеет напрямую настраивать оборудование MikroTik (модели hEX, hAP) через CLI RouterOS — так же, как современные coding-агенты работают через bash/PowerShell. Цель — автоматизировать рутинную однотипную настройку сетевого оборудования на работе (провайдер интернета).

**Как это должно работать в общих чертах (полная картина, для контекста агента):**

1. **Блок A — Connect.** Человек запускает `mth`, видит список доступных MikroTik в сети (как Neighbors в WinBox), выбирает устройство, вводит логин/пароль, подключается. LLM здесь не участвует.
2. **Блок B — агентный цикл.** После подключения человек ставит задачу на естественном языке («настрой bridge + PPPoE с такими-то логином/паролем»). LLM-агент рассуждает, обращается к базе знаний (RAG по официальной документации MikroTik) и выполняет команды через SSH-сессию, открытую в Блоке A.
3. **Блок C — safety layer.** Все сессии агента обязаны стартовать в Safe Mode RouterOS (не опционально). Разрушительные изменения (firewall, bridge, routes, адреса) идут через шаг подтверждения человеком (preview/diff), не выполняются автоматически.
4. **Блок D — интерфейс.** Сначала весь функционал — CLI (аналог headless-движка вроде llama.cpp: движок отдельно, интерфейс — тонкий клиент поверх него). Визуальная обвязка (сворачиваемые блоки рассуждений, загрузка файлов/фото) добавляется позже поверх того же бэкенда.

**Модели:** локальные через LM Studio/Ollama (Qwen, Gemma) либо через API (OpenRouter) — выбор модели не блокирует архитектуру, бэкенд должен быть модель-агностичным.

**Нефункциональные требования, которые нельзя нарушать:**
- Safe Mode обязателен для каждой сессии агента, не рекомендация.
- Любое изменение конфигурации проходит через подтверждение человеком, кроме read-only команд.
- Полный лог команда → ответ для каждой сессии.

## Раздел 2. Блок A — подключение к MikroTik (замена WinBox в CLI)

### Цель блока
Пользователь запускает `mth` в терминале и получает функциональность стартового окна WinBox: живой список доступных в сети устройств (Neighbors), поля для ручного ввода адреса/логина/пароля, подключение — без участия LLM. Результат работы блока — открытая, проверенная SSH-сессия, готовая к передаче в Блок B.

### Технологический стек
- **Python 3.11+**
- **Textual** (TUI-фреймворк, asyncio-нативный, живые виджеты, DataTable, Input с маскировкой пароля, keybindings) — обеспечивает уровень интерфейса, сопоставимый с современными agentic CLI, без выдумывания велосипеда с raw ANSI-последовательностями.
- **asyncssh** — SSH-клиент на asyncio (не paramiko, чтобы жить в одном event loop с Textual и не городить потоки).
- Точка входа: `console_scripts` в `pyproject.toml` → команда `mth` доступна в PATH после `pip install -e .`.

### Discovery (MNDP)
- Протокол: MikroTik Neighbor Discovery Protocol, широковещательные UDP-пакеты на **порт 5678**.
- Формат: TLV (тип 16 бит + длина 16 бит, big-endian), поля включают MAC-адрес, Identity, версию RouterOS, платформу/board, uptime, interface.
- Устройство анонсирует себя пассивно раз в ~60 секунд — при чисто пассивном прослушивании список наполняется медленно.
- **Refresh должен быть активным**: отправить broadcast-пробник (форсирующий пакет), затем слушать ответы 2-3 секунды — так поведение будет как в WinBox (быстрый список), а не как пассивный sniffer.
- Не реализовывать TLV-парсинг с нуля по памяти — взять за референс готовую рабочую реализацию: `github.com/petrunetworking/MNDP-Mikrotik-Neighbor-Discover-Python` (декодирует MAC/Identity/Version/Board из живых пакетов). Альтернативный референс — `github.com/bgptools/mndp`. Для точной структуры TLV-типов, если референсы разойдутся, свериться с Wireshark-диссектором `packet-mndp.c`.
- MAC-based подключение (без IP, как в «Connect To RoMON» или прямое подключение по MAC) — вынести за скобки v1, это отдельный сложный протокол поверх raw Ethernet-фреймов. В первой версии — только подключение по IP.

### UI-композиция (Textual)
- **DataTable**: колонки MAC / IP / Identity / Version / Board. Наполняется асинхронно фоновой задачей-слушателем MNDP (`run_worker`), обновляется реактивно по мере прихода пакетов.
- **Input(password=False)** — поле "Connect To": заполняется вручную ИЛИ автоматически при выборе строки в таблице (курсор + Enter на строке копирует IP в поле). Обязательно оставить ручной ввод — не все устройства попадают в broadcast-домен (VLAN, другой сегмент).
- **Input(password=True)** — поля Login / Password.
- Статус-строка внизу экрана: `Поиск устройств...` → `Подключение...` → `Подключено к <identity> (<board>, RouterOS <version>)` / текст ошибки.
- Keybindings: стрелки/j-k — навигация по таблице, Tab — между полями, `r` — refresh (активный пробник), Enter на поле пароля или отдельный биндинг — запуск подключения, `q` — выход.

### Подключение и хэндовер в Блок B
- По команде Connect: открыть persistent PTY-сессию через asyncssh (`open_session` с террминальным типом) — **не** exec-канал на каждую команду, так как:
  - Safe Mode RouterOS — свойство одной непрерывной терминальной сессии, а не отдельного вызова;
  - контекст текущего меню CLI (`/interface bridge>` и т.п.) тоже живёт только в рамках одной сессии.
- Сразу после открытия сессии — активировать Safe Mode (Ctrl+X/0x18 в терминале) как обязательный шаг, не опциональный.
- Проверочная команда сразу после подключения: `/system identity print` (или `/system resource print`) — подтверждает, что сессия реально работает и что это RouterOS, и заодно тестирует framing-механизм (см. ниже).
- Framing вывода команд: интерактивный shell не даёт чистого EOF на команду. Использовать sentinel-маркер — после каждой отправленной команды дописывать служебную команду с уникальным маркером (`:put "CMD_DONE_<uuid>"`), читать поток до появления маркера, обрезать его из вывода. Это даёт надёжную границу ответа независимо от длины команды и не полагается на парсинг изменчивого prompt'а.
- Результат работы блока — открытый объект SSH-сессии + функция `send_command(cmd) -> str`, которую использует Блок B.

### Критерий готовности (definition of done)
1. `mth` запускается, в течение нескольких секунд без нажатия Refresh в таблице появляется реальный MikroTik из локальной сети (пассивный listen).
2. `r` — таблица обновляется быстрее за счёт активного пробника.
3. Выбор строки стрелками + Enter — IP копируется в поле Connect To.
4. Ручной ввод IP в Connect To (без выбора из таблицы) тоже работает.
5. Заполнение Login/Password (с маскировкой) и запуск Connect — открывает SSH-сессию, включает Safe Mode, отправляет проверочную команду через sentinel-framing и получает корректный ответ.
6. Статус-строка показывает identity/board/версию подключённого устройства.
7. Ошибки подключения (неверный пароль, недоступный хост) отображаются в статус-строке, не роняют программу.

## Раздел 3. Блок B — агентный цикл (chat-интерфейс поверх подключения)

### Цель блока
После успешного Connect (конец Блока A) пользователь попадает в chat-интерфейс, визуально повторяющий Claude Code CLI / Codex CLI: строка ввода снизу, статусная шапка сверху, LLM-агент выполняет задачи через tool calling по SSH-сессии, открытой в Блоке A, опираясь на RAG и заранее заданный системный промпт.

### Тестовое окружение
Основной стенд для отладки Блока B — виртуальная RouterOS (**CHR, Cloud Hosted Router**), рабочая VM с полноценной RouterOS, физическое оборудование не требуется. Все итерации агентного цикла и тестовые задачи в первую очередь прогоняются на ней, физическое устройство — для финальной проверки.

### Шапка интерфейса (header)
Выводится при старте чата и по команде `/info` (если чат длинный и шапка ушла из вида):
- Логотип: "MikroTik" (ч/б стиль) + "Harness" (акцентный стиль)
- Текущая модель LLM и провайдер
- Версия mth
- Данные подключённого устройства: MAC, IP, Identity, RouterOS Version, Board — это НЕ новый запрос к устройству, а проброс структуры, уже собранной в конце Блока A (`$model_mikrotik` и остальные поля)
- Несколько стартовых подсказок (`/help` и т.п.)

### Список команд (v1, минимально необходимый)
- `/help` — список команд
- `/info` — повторный вывод шапки
- `/model` — визард выбора/настройки модели (см. ниже)
- `/models` — список сохранённых пресетов, быстрый выбор
- `/effort` — уровень reasoning (если провайдер/модель это поддерживает — нюанс ниже)
- `/log` — история команд текущей сессии (аудит-лог команда → ответ)
- `/resume` — восстановить предыдущую сессию (история диалога + переподключение к устройству)
- `/clear` — очистить контекст диалога без разрыва SSH-сессии
- `/exit` — закрыть сессию, вернуться в Блок A

Правило разбора ввода: строка, начинающаяся с `/`, — всегда команда харнесса; всё остальное — естественноязыковой запрос к агенту. Прописать это явно в парсере, чтобы не было двусмысленности.

### `/model` — визард выбора провайдера
Три ветки:
1. **Local** — харнесс проверяет, поднят ли LM Studio бэкенд (если нет — просит поднять/поднимает сам), запрашивает список загруженных моделей, пользователь выбирает.
2. **OpenRouter** — URL зашит константой, пользователь вводит только API-ключ и имя модели.
3. **Сторонний OpenAI-совместимый провайдер** — URL, API-ключ, имя модели вводятся вручную.

Каждая настроенная связка сохраняется как **пресет** (имя → провайдер/URL/модель), быстрый выбор — через `/models`.

**Безопасность пресетов:** API-ключи не хранить открытым текстом в конфиге пресетов (риск случайного попадания в git). В пресете — только провайдер/URL/модель, ключ — через переменную окружения или системный keyring, подставляется в рантайме.

### Активация модели (warm-up)
- После выбора модели/пресета — короткий тестовый запрос («ты тут?»), скрытый от пользователя.
- Обязательно без thinking-режима — механизм отключения различается по провайдерам (где-то параметр API вроде `enable_thinking=False`, где-то суффикс в промпте, где-то через OpenRouter thinking не всегда управляем в принципе) — закладывать per-provider конфигурацию, не единый флаг.
- Замер скорости (t/s) во время прогрева, фоново, без вывода пользователю.
- Провал warm-up — конкретная причина, а не общая ошибка: нет интернета / нет связи с провайдером / неверный URL / неверный API-ключ / неверное имя модели — перечислить как отдельные состояния ошибки в коде.

### Системный промпт (AGENTS.md) — требования к содержанию
Фиксируем ТРЕБОВАНИЯ к разделам; сам текст промпта пишется позже, после тестирования на CHR:
1. **Роль/экспертиза** — опытный сетевой инженер, эксперт по MikroTik, знает модель OSI и т.д.
2. **Контекст размещения** — где находится модель (MikroTik Harness), зачем существует харнесс, зачем существует само оборудование.
3. **Данные о конкретном устройстве** — информация о подключённой модели устройства (порты, назначение, возможности). Реализовать как таблицу данных (JSON/YAML: `{"hex": {...}, "hap": {...}}`), а не как цепочку `if/elif` в коде — добавление нового устройства должно быть правкой данных, а не кода.
4. **Роль агента и инструменты** — объяснение, что модель — агент с доступом к CLI устройства через tool calling, как именно выполняются команды, что такое RAG в её контексте и как им пользоваться.
5. **Safe Mode** — объяснение, что сессия по умолчанию в Safe Mode и зачем.
6. **Стартовые команды-подсказки** — пара типовых команд для старта.
7. **Golden-path примеры** (см. ниже) — место в промпте под 2-3 эталонных сценария успешной настройки.

### Три слоя промпта на каждый запрос
1. Системный промпт (AGENTS.md) — фиксированный, решает половину задачи заранее.
2. Промпт пользователя — конкретная задача на естественном языке.
3. RAG — данные по теме запроса: либо проактивно добавлены харнессом по ключевым словам, либо запрошены самой моделью через инструмент поиска (агент сам решает, когда).

Модель должна распознавать недостаток информации в запросе (например «настрой bridge и firewall» без указания интерфейсов) и задавать уточняющий вопрос вместо угадывания — прописать это в системном промпте как ожидаемое поведение явно.

### Golden-path — фиксация эталонных решений
- Требование к процессу, не к реализации в v1: при тестировании на CHR документировать каждую тестовую задачу — успех/провал, весь путь модели, включая неверные попытки.
- Из успешных сессий вручную вычищать шум (неверные/лишние команды), оставлять только чистый правильный путь.
- Вычищенные сценарии позже вручную добавляются в AGENTS.md как few-shot примеры.
- Отдельная автоматизация для этого в v1 не нужна — обычного лога команда→ответ достаточно, чтобы позже вручную отобрать хорошие примеры.

### Отображение рассуждений агента (UI)
Опирается на event-стрим, заложенный ранее в архитектуре (`reasoning` / `tool_call` / `tool_result` / `text` как типизированные события) — новой инфраструктуры не требуется, только рендер:
- Каждый шаг рассуждения — сворачиваемый блок ("Thinking...", разворачивается по клику)
- Каждый вызов инструмента — отдельный сворачиваемый блок со своей иконкой (RAG-поиск, SSH-команда и т.д.)
- В конце пачки шагов — короткое резюме одной строкой (что исследовано/сделано) — вопрос форматирования вывода, не новой инфраструктуры.

### `/effort` — уровень reasoning
Не все провайдеры одинаково поддерживают управляемый уровень рассуждений (у части API есть параметр вроде `reasoning_effort`, у локальных моделей через LM Studio/Ollama — часто только грубый вкл/выкл thinking, без градации). Команда должна проверять поддержку у текущего провайдера/модели и явно сообщать, если параметр не поддерживается, а не молча игнорировать выбор.

### Незакрытые вопросы — зафиксировать решение сейчас
- **Смена модели посреди диалога (`/model` в разгар работы)**: история диалога сохраняется; для новой модели/провайдера обязательно заново прогоняется warm-up-хендшейк перед продолжением работы.
- **`/resume` между запусками `mth`**: нужно решить, сохраняется ли сессия (история диалога + к какому устройству была подключена) на диск между перезапусками программы, или живёт только в рамках текущего процесса.

### Критерий готовности (definition of done) для Блока B
1. После Connect пользователь видит шапку: логотип, модель, версия mth, данные устройства.
2. `/model` проводит по всем трём веткам выбора провайдера и сохраняет пресет (без API-ключа в открытом виде).
3. `/models` показывает сохранённые пресеты; выбор пресета автоматически проходит warm-up.
4. Провал warm-up показывает конкретную причину ошибки, не общую.
5. Естественноязыковой запрос пользователя доходит до модели вместе с системным промптом (плейсхолдер на этом этапе, не финальный текст) и RAG-контекстом при необходимости.
6. Модель, получив неполный запрос, задаёт уточняющий вопрос вместо угадывания.
7. Каждый шаг агента (thinking / tool_call / tool_result / text) виден пользователю как сворачиваемые блоки.
8. Весь цикл тестируется в первую очередь на CHR VM, без необходимости в физическом MikroTik.
